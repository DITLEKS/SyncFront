# Отчёт по шагу 4 — редактор правок

Дата: 04.10.2026. Бэкенд: `DITLEKS/SyncBack main @ 6acd173`. Ветка фронта: `feat/04-editor` (от `main @ cdf7790`).

## Что сделано

### Домен (`src/domain/editor`, без React)

- `suggestion.ts` — словарь правок: типы `modify | add | delete`, статусы, подписи и цвета разметки
  (изменение — жёлтый, добавление — зелёный, удаление — красный). Совпадение с контрактом проверяется типами в `src/api/types.ts`.
- `projection.ts` — `buildProjection()` строит текст с правками по правилам экспортёров SyncBack
  (`TextExporter` / `DocxExporter`, перечитаны на `6acd173`):
  - принятые правки применяются по очереди в порядке ответа сервера `(created_at, id)`, каждая — к уже изменённому тексту;
  - `modify`/`delete` — первое вхождение `original_text` во всём тексте; для `docx`/`doc` фрагмент с переводом строки не применится,
    потому что сервер ищет внутри одного абзаца;
  - `add` — в конец документа (в «Чистовике»); в «Правках» — в конце раздела `section_ref`, чтобы читать в контексте;
  - для каждой правки вычисляется `issue`: `not_found`, `overlap`, `not_applicable`, `outside_section`, и признак `exportable`;
  - офсеты разделов сервер считает в кодовых точках Python, строки JS — в UTF-16: `sectionsInUtf16()` пересчитывает их,
    если в тексте есть суррогатные пары.
  - `exportedText()` — текст, который получится при экспорте. В тестах он сравнивается с построчным переносом серверных экспортёров
    на txt, md и docx, включая спецсимволы замены `$&`.
- `review.ts` — правила буфера: `effectiveStatus`, `planSave` (решения только по серверным `pending`;
  `finalize = true` только если после сохранения `pending` станет 0, иначе сервер ответит 409), `reviewProgress`.

### API (`src/api/resources/editor.ts`)

- `getEditor` — `GET …/editor?suggestions_limit=200`, остальные страницы догружаются через `GET …/suggestions?limit=200&offset=…`:
  буферу и разметке нужен полный список.
- `saveReview` — `PUT …/suggestions/review` с `If-Match: <review_version>` и тем же `review_version` в теле.
- `resetSuggestionDecisions` — `PATCH …/suggestions {ids, status: "pending"}` для отмены уже сохранённого решения.
- `resetReview` — `POST …/editor/reset`.
- `exportDocument` — `GET …/export` без `export_format` (R-1), ответ как `Blob`, имя файла — из `Content-Disposition`
  (`filename*` RFC 5987, затем `filename`, затем название документа).

### Экран (`features/editor`)

- Страница документа в `awaiting_approval` и `ready` показывает редактор вместо статус-панели; для `draft` и `in_progress` всё как на шаге 3.
- Верхняя панель: «Назад» (на предыдущую запись истории, а если страницу открыли по ссылке — на проект), название, статус,
  «На рассмотрении» и «Принято» с учётом несохранённых решений, переключатель «Оригинал / Правки / Чистовик», «Проверить актуальность»
  (в `ready`), «Экспорт», «Сохранить / Сохранено», меню «…» с «Сбросить все изменения».
- Переключатель режимов: подложка активного пункта переезжает с пружинной кривой (`sliding` в `SegmentedControl`,
  без библиотеки анимаций, с `motion-reduce`). Начальный режим — из `document.view_mode`.
- «Оригинал»: исходный текст без разметки и уведомление «Открыт исходный текст до предложений ИИ…».
- «Правки»: все правки размечены; удаляемое зачёркнуто, добавляемое выделено цветом; рассмотренные приглушены,
  у отклонённой зачёркнут предложенный вариант.
- «Чистовик»: рассмотренные правки — обычный текст (принятые применены, отклонённые нет), нерассмотренные размечены.
- Панель «Предложения ИИ»: «X из N · P%» и полоса прогресса; фильтр «На рассмотрении / Решено / Все» со счётчиками
  и пустыми состояниями; карточки: тип, краткий текст, раздел, решение («· не сохранено» для буфера), значок предупреждения.
  Длинный список дорисовывается по 100 карточек кнопкой «Показать ещё».
- Выбор карточки прокручивает текст к фрагменту и выделяет его; клик по фрагменту в тексте (или Enter/пробел) выделяет карточку.
- Карточка правки: тип, раздел, обоснование («ИИ не указал обоснование», если `rationale = null`), уверенность ИИ,
  текущий и предлагаемый текст, для удаления — «Выбранный фрагмент будет удалён.», для добавления — пометка про конец документа,
  предупреждение по `issue`. Кнопки «Принять» / «Отклонить» (только при `permissions.can_review`) и «Отменить» для решённых.
  Карточка закрывается после решения, крестиком и при выборе другой правки.
- Буфер решений — Zustand, привязан к `document_id + current_analysis_job_id`: перезапрос редактора (SSE, конфликт) его не теряет,
  новый анализ его сбрасывает. Решения по правкам, которые на сервере уже не `pending`, из буфера убираются.
- «Отменить»: несохранённое решение снимается локально; сохранённое — сразу `PATCH {ids, status: "pending"}`
  (в `ready` документ возвращается в `awaiting_approval`).
- Сохранение: `PUT /review`. Ошибка 412/409 → баннер «Документ изменён в другой сессии», перезапрос `GET /editor`, буфер остаётся,
  повторное «Сохранить» уходит с новым `If-Match`. Прочие ошибки — блок «Не удалось сохранить изменения» с текстом сервера,
  кнопка остаётся активной.
- Завершение: когда `pending` = 0, в панели блок «Все предложения обработаны. Сохраните или экспортируйте документ.»
  с «Сохранить» и «Просмотреть чистовик»; после сохранения — «Проверка завершена. Документ получил статус «Готово».»
- Экспорт: меню с одним пунктом — исходным форматом (`.md`, `.docx`, `.txt`), доступно только при `permissions.can_export`;
  иначе кнопка неактивна с подсказкой «Экспорт доступен после сохранения всех решений».
- «Сбросить все изменения»: подтверждение с текстом из «Описания UI», затем `POST /editor/reset` и очистка буфера.
- Уход со страницы с несохранёнными решениями: `useBlocker` (переходы внутри приложения) и `beforeunload` (закрытие вкладки).
  Окно «Есть несохранённые изменения. Покинуть страницу без сохранения?» с «Сохранить и выйти», «Выйти без сохранения», «Остаться».
- SSE: событие смены статуса инвалидирует `documents.*`, в том числе ключ редактора; буфер при этом сохраняется.

  на реальном файле не проверялось.

## Гипотезы

- Если сервер когда-нибудь начнёт присылать `start_offset`/`end_offset`, разметку стоит строить по ним, а поиск оставить запасным путём.
- `overlap` встречается, когда модель предлагает две правки одного места; если это частый случай, лучше дедуплицировать их на сервере.
