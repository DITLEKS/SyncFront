# Архитектура фронтенда SyncScribe (SyncFront)

Дата: 04.10.2026. Бэкенд: [DITLEKS/SyncBack](https://github.com/DITLEKS/SyncBack), `main @ 609ce98` (после PR #64).
Контракт сверен не с README, а с кодом: `openapi.json` сгенерирован из `app.main` (35 путей, 44 операции),
прочитаны `app/domain/lifecycle.py`, `app/api/v1/routers/{sse,editor,documents}.py`,
`app/infrastructure/exporters/*`, `app/main.py` (CORS, обработчики ошибок).

Документ отвечает на два вопроса: что в бэкенде определяет форму фронтенда и как фронтенд устроен,
чтобы оставаться чистым при росте.

## 1. Что в бэкенде важно для фронтенда

### 1.1. Бэкенд уже спроектирован по DDD — фронт повторяет его словарь

| Слой SyncBack                                           | Что там                                                                                                                      | Что это значит для фронта                                                                                                                                                                                                            |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

В редакторе приоритет у `permissions` из `GET /editor`; `documentPolicy` нужен в списках, где `permissions` нет         |
| `domain/value_objects.py`                               | `DocumentStatusVO` (4 статуса), `AnalysisJobStatusVO` (7), `SourceScopeVO`, `DocumentFormatVO`                               | Словарь домена фронта (`DocumentStatus`) объявлен независимо, а совпадение с OpenAPI проверяется на уровне типов (`src/api/types.ts`, `documentStatusContractMatches`). Дрейф контракта ломает `typecheck`, а не UI в рантайме       |

| `main.py`                                               | CORS без `*`, `expose_headers: Content-Disposition, Retry-After`; `DomainError → 400`, валидация → 422 с массивом `detail`   | `getErrorMessage` разбирает оба формата `detail`, 429 дополняет `Retry-After`; имя файла экспорта читается из `Content-Disposition` (`filename*`, затем `filename`)                                                                  |

### 1.2. Факты контракта, которые определяют архитектуру

- **Статусы.** Документ — ровно 4 публичных статуса; техническое состояние анализа — отдельное поле `analysis`
  (`state`, `error_code`, `error_message`, `can_retry`). Ошибка анализа не статус, а причина у `draft`.
- **Сервер не меняет текст при принятии правок.** `content.plain_text` и `original_content.plain_text` в `GET /editor` —
  один и тот же исходный текст. Режимы «Правки» и «Чистовик» — чисто клиентская проекция (`domain/editor/applySuggestions.ts`, шаг 4).
- **Ревью — оптимистическая блокировка.** `PUT /suggestions/review` с `If-Match: <review_version>`; `412` — версия устарела,
  `409` с `finalize=true` при остатке `pending`. Клиент обязан сам вычислять `finalize` и не допускать 409.
- **Одна активная задача на документ, идемпотентный запуск.** `Idempotency-Key` (UUID v4 на клик); из `ready` — только `force=true`
  после подтверждения (`409 { confirmation_required: true }`).
- **Источники заморожены** в `in_progress` и `awaiting_approval` (`423`).
- **Чужой ресурс — 404**, не 403. UI не различает «нет» и «не моё».
- **Токены.** Refresh ротируется, повторное использование старого — `401`. Отсюда single-flight refresh с общей очередью.

### 1.3. Как сервер применяет правки при экспорте (определяет «Чистовик»)

Прочитано в `TextExporter.apply_changes` и `DocxExporter.apply_changes`:

| Тип      | txt / markdown                                                                      | docx                                                                 |
| -------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `modify` | `text.replace(old, new, 1)` — **первое вхождение во всём тексте**, не внутри секции | первый абзац, содержащий `old`; внутри абзаца `replace(old, new, 1)` |
| `delete` | `text.replace(old, "", 1)`                                                          | то же, с пустой заменой                                              |
| `add`    | `text.rstrip("\n") + "\n\n" + new + "\n"` — **в конец документа**                   | `document.add_paragraph(new)` — **в конец документа**                |

Правки применяются последовательно в порядке `(created_at, id)`, каждая — к уже изменённому тексту.

Следствия для клиента:

1. Поиск `original_text` — первое вхождение во всём `plain_text`, как на сервере. `section_ref` используется для навигации
   и для предупреждения «фрагмент найден вне указанной секции», но не для выбора вхождения. Иначе «Чистовик» и экспорт разойдутся,
   если тот же фрагмент встречается раньше в другой секции.
2. `add` в «Чистовике» показывается в конце документа (как в экспорте). В режиме «Правки» карточка добавления привязана к `section_ref`
   для удобства чтения, с пометкой «при экспорте будет добавлено в конец документа». Это расхождение с ожиданием UI-описания
   («добавление нового текста или раздела» рядом с контекстом) вынесено в «Открытые вопросы»: правильное место для исправления — экспортёр.
3. Пересекающиеся правки: если `original_text` двух правок пересекаются в тексте, UI показывает предупреждение — сервер применит
   вторую к уже изменённому тексту и, скорее всего, не найдёт вхождение.

## 2. Принципы

1. **Домен не знает о React и HTTP.** `src/domain/**` — чистый TypeScript: статусная модель, политика действий, применение правок,
   буфер решений ревью. Это самый тестируемый и самый рискованный код; он покрывается unit-тестами без DOM.
2. **Один источник правды на каждое знание.** Лейблы и цвета статусов — `statusMeta`; ключи кеша — `queryKeys`; разбор ошибок —
   `getErrorMessage`; лимиты загрузки — `useCapabilities()`; пути — `routes`.
3. **Сгенерированный контракт — граница.** `openapi.d.ts` не редактируется; всё, что контракт выражает слабо, уточняется в `api/types.ts`.
   Это антикоррупционный слой между транспортом и доменом фронта.
4. **Серверное состояние ≠ локальное состояние.** Серверное — только в TanStack Query (кеш, инвалидация, SSE-патчи).
   Локальное — Zustand только там, где есть настоящая клиентская модель: буфер решений редактора, выбранная правка, режим просмотра.
   Никакого дублирования серверных данных в сторах.
5. **Фича — bounded context с публичным API.** Снаружи фичи доступен только `index.ts`. Это проверяет ESLint (`eslint-plugin-boundaries`),
   а не договорённость.
6. **Честные состояния.** Каждый экран имеет загрузку (скелетоны), пустое состояние (тексты из UI-описания дословно) и ошибку
   (сообщение сервера + «Повторить»). Нет «хаков» вроде повторов до успеха.

## 4. Ключевые механизмы

### 4.1. Аутентификация (реализовано на шаге 1)

- `authSession` — модуль без React. Access-токен в памяти, refresh — в `localStorage` (осознанный компромисс: бэкенд не ставит httpOnly cookie).
- Refresh — single-flight: параллельные вызовы получают один промис; новая пара сохраняется атомарно до резолва ожидающих.
  Любая ошибка refresh очищает сессию и уведомляет подписчиков (`AuthProvider` → `/login?returnTo=`).
- Проактивное обновление за 60 с до `expires_in` (таймер) и реактивное на 401 (middleware клиента, ровно один повтор на запрос;
  копия запроса делается в `onRequest`, потому что тело оригинала уже прочитано).
- `AuthProvider` восстанавливает сессию при старте одним refresh, затем `GET /auth/me` через TanStack Query. Регистрация не выдаёт токены — сразу вызывается login.
- Rate limit (429) показывается с `Retry-After`, запрос не повторяется.

### 4.2. Серверное состояние и инвалидация

- Ключи — `queryKeys` с иерархией (`['documents', 'project', id, params]`), чтобы инвалидировать срезами.
- Мутации инвалидируют по ключам; оптимистические обновления только в буфере решений редактора (это локальное состояние, а не кеш сервера).
- SSE-событие `document_status_changed` → `setQueryData` для детали документа (статус и `current_analysis_job_id`) и инвалидация списков,
  дашборда, attention/recent; для открытого редактора — повторный `GET /editor` с сохранением буфера.

### 4.3. Реальное время (шаг 3)

Один `SseProvider` внутри защищённого layout: `fetch` + `ReadableStream` + `createSseParser`, `AbortController`, переподключение
с экспоненциальной задержкой 1→30 с, при 401 — сначала `authSession.refresh()`, watchdog «нет `ping` > 60 с → переподключиться».
Fallback: пока соединения нет, документы в `in_progress` опрашивают `GET …/analysis-jobs/{j}` раз в 5 с (`refetchInterval` зависит от флага `sse.connected`).

### 4.4. Редактор (шаг 4)

Доменная модель в `src/domain/editor/`:

- `locateSuggestion(plainText, suggestion)` — позиция по правилам сервера (§1.3), с признаком «найдено в другой секции / не найдено».
- `buildView(plainText, suggestions, decisions, mode)` — список блоков по абзацам с сегментами `plain | modify | add | delete`,
  где решение берётся из локального буфера поверх серверного статуса. Мемоизация по абзацам.
- `detectOverlaps(located)` — пересечения диапазонов для предупреждения.
- `reviewBuffer` (Zustand) — `Map<suggestionId, decision>` несохранённых решений, `isDirty`, `planSave(serverSuggestions)` →
  `{ decisions, finalize }`, где `finalize = true` только если после применения `pending_count` станет 0.

Сохранение: `PUT …/suggestions/review` с `If-Match`; `412`/`409` версии → баннер «Документ изменён в другой сессии», перезапрос
`GET /editor`, буфер сохраняется и предлагается к повторному применению. Уход со страницы с непустым буфером — `useBlocker` + `beforeunload`.
Отмена уже сохранённого решения — `PATCH {ids, status: "pending"}` сразу (работает и в `ready`, документ возвращается в `awaiting_approval`).

### 4.5. Загрузка документа

Двухэтапный диалог: `POST /projects/{p}/documents` → источники `scope=document` → `POST …/analysis-jobs` с `Idempotency-Key`.
Нет транзакции: закрытие после первого этапа оставляет документ в `draft` — это ожидаемо и показывается честно.
Проверка расширения и размера на клиенте — из capabilities; 413/415/422 сервера показываются как есть.

## 5. Качество

- `strict` TypeScript, `noUncheckedIndexedAccess`, запрет `any`; `typescript-eslint strictTypeChecked`.
- Тесты: unit для домена (`applySuggestions`, буфер решений, `sseParser`, `authSession`, `getErrorMessage`), интеграционные с MSW
  на сценарии (вход → проект → загрузка → анализ (SSE) → ревью → сохранение → экспорт).
- Доступность: `FormField` связывает label/hint/error через `aria-describedby`; у иконок-кнопок `aria-label`; фокус-кольцо только для клавиатуры;
  Radix-примитивы для меню, диалогов и тултипов.
- Производительность: vendor-чанки (`react`, `query`, `forms`), debounce поиска 300 мс, виртуализация списка правок при > 200, мемоизация разметки по абзацам.

## 6. Решения (ADR в одну строку)

| №   | Решение                                                                 | Почему                                                                                     |
| --- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| A-1 | Домен фронта независим от `openapi.d.ts`, совпадение проверяется типами | Антикоррупционный слой; дрейф ловится на `typecheck`                                       |
| A-2 | Границы слоёв и публичные `index.ts` фич проверяет ESLint               | Договорённости без проверки не живут                                                       |
| A-3 | Refresh в `localStorage`, access в памяти                               | Нет httpOnly cookie на бэкенде; XSS-риск компенсируется коротким access и ротацией refresh |
| A-4 | Один SSE-канал на приложение без `document_ids`                         | Событий мало, фильтр усложняет навигацию                                                   |
| A-5 | «Чистовик» повторяет алгоритм экспортёров сервера, а не UI-интуицию     | Иначе экспорт не совпадёт с тем, что видит пользователь                                    |
| A-6 | `export_format` не передаётся                                           | На сервере `md ≠ markdown`; исходный формат выбирается сам                                 |
| A-7 | После создания проекта — переход на его страницу                        | UI-описание оставляло выбор; следующий шаг пользователя — добавить источники и документы   |
| A-8 | Tailwind 3.4 + ручные shadcn-примитивы                                  | Стабильная связка с React 18; `components.json` позволяет добавлять компоненты CLI         |

## 7. Открытые вопросы к владельцу

1. **R-2 (`add` в конец документа).** Оставить как есть и показывать пометку, или поправить экспортёр, чтобы вставка шла после секции `section_ref`
   (тогда клиент и сервер смогут одинаково привязывать добавления)?
2. **R-3 (поиск по всему тексту).** Нужна ли серверу привязка к секции при замене (`section_ref` + `start_offset`), когда модель начнёт отдавать офсеты?
3. **Диалог подтверждения повторного анализа из `awaiting_approval`.** Сервер запускает без подтверждения и сбрасывает решения. Показывать клиентский диалог? (Предлагаю да, с тем же текстом.)
4. **`original_content` в `GET /editor`** дублирует `content` (F-7). Фронт использует только `content`; поле можно убрать.
5. **Пароль:** политика сложности видна только по тексту 422. Если появится описание политики в `/system/capabilities`, подсказку под полем можно сделать точной.
